# Spec: F1 Gap Research

Status: ready-for-agent

术语以根目录 `CONTEXT.md` 为准；数据访问方式见 `docs/adr/0001`。

## Problem Statement

一场 F1 比赛结束时，观众看到的只是一个数字：两名车手并排发车，九十分钟后一个领先另一个 25 秒。这 25 秒是从哪里来的？是他在赛道上确实更快，是车队在进站时做对了决定，还是安全车恰好在对他有利的时刻出现？

解说和赛后报道会给出说法，但普通观众没有时间也没有能力去核对逐圈数据，所以分不清哪些说法有依据，哪些只是讲故事。通用的大模型也帮不上忙：2026 赛季的比赛它并不知道，只会给出听起来合理但无法核对的答案。

## Solution

一个 Deep Research 助手。用户用自然语言问一场 2026 赛季 Race 里一对 Driver Pair 的差距，助手逐圈重建 Gap，找出 Gap 发生变化的 Gap Phase，派出并行的 Researcher 分别调查每个阶段，最后给出一份报告：

- 简短结论：Gap 主要在哪些 Gap Phase 形成，各占多少秒。
- Gap 曲线图：标出进站、安全车和各个 Gap Phase。
- 每个关键 Gap Phase 的分析：圈速、轮胎、进站、赛事事件。
- 每个 Explanation 标明 Support Level；数据回答不了的部分明确说出来。
- 每个事实都带 Evidence 编号，可以点开核对原始数据。

## User Stories

1. 作为 F1 观众，我想问"某场比赛里 A 为什么比 B 慢了这么多"，以便知道最终差距是在哪里形成的。
2. 作为 F1 观众，我想看到 Gap 随圈数变化的曲线图，以便一眼看出差距在哪几圈拉开。
3. 作为 F1 观众，我想让图上标出进站和安全车，以便把 Gap 的变化和比赛事件对上。
4. 作为 F1 观众，我想知道每个 Gap Phase 贡献了多少秒，以便分清主要原因和次要原因。
5. 作为 F1 观众，我想知道某个 Gap Phase 里两人的轮胎配方和胎龄，以便判断轮胎是否能解释圈速差。
6. 作为 F1 观众，我想知道两人每次进站各花了多少时间，以便判断差距有多少来自维修区。
7. 作为 F1 观众，我想知道安全车、虚拟安全车、红旗和处罚发生在哪几圈，以便判断它们对 Gap 的影响。
8. 作为 F1 观众，我想让每个 Explanation 标明 Support Level，以便区分有数据支持的结论和只是与数据不矛盾的猜测。
9. 作为 F1 观众，我想在数据回答不了时被明确告知（例如车手失误、赛车损伤、车队指令），以便不被编造的理由误导。
10. 作为 F1 观众，我想点开报告里的 Evidence 编号看到对应的数据行和来源，以便自己核对。
11. 作为 F1 观众，我只说了一名车手或没说清是哪场比赛时，想让助手带着候选项反问我，以便一步就能把问题补全。
12. 作为 F1 观众，我想在同一个对话里追问（例如"第二次进站呢？"），以便不用重复说比赛和车手。
13. 作为 F1 观众，我只关心某一方面（例如进站策略）时，想得到聚焦的短报告，而不是每次都面面俱到。
14. 作为 F1 观众，我想在等待时看到 Lead、各个 Researcher 和 Writer 正在做什么，以便知道助手没有卡住，也理解结论是怎么来的。
15. 作为 F1 观众，我问到退赛或被套圈的车手时，想被告知 Gap 只算到两人都完成的最后一圈，以便正确理解数字。
16. 作为 F1 观众，我问到范围之外的内容（排位赛、冲刺赛、其他赛季）时，想被直接告知不支持，以便不浪费时间。
17. 作为不看 F1 的访客，我想在页面上看到这个助手探索什么、给谁用、怎么用，以及可以点击的示例问题，以便马上试用。
18. 作为用中文提问的用户，我想得到中文报告，以便阅读。
19. 作为评分者，我想让 `POST /chat` 返回和 Project1 相同的结构，并且子 agent 的工具调用也在 `tool_calls` 里带 `agent` 字段，以便检查助手的工作过程。
20. 作为评分者，我想在 5 分钟内拿到回答，以便完成测试。
21. 作为评分者，我想在 README 里看到三个示例问题、预期答案、数据出处，以及同一模型不带工具时的回答，以便衡量助手的效果。
22. 作为维护者，我想在新比赛结束后重跑一个脚本就能更新快照，以便助手覆盖最新的 Race。

## Implementation Decisions

- **数据**：离线脚本从 OpenF1（逐圈圈速与三段计时、stint、进站、race control、超车、位置、天气、成绩）和 Jolpica（发车位、官方成绩）拉取 2026 赛季全部正赛，生成本地快照并提交进仓库。线上不调用外部 API，不需要任何 secret。
- **Gap 计算**：按 `CONTEXT.md` 的定义，由逐圈数据算出每圈过线时刻之差。红旗、安全车时段和进站圈强制成为 Gap Phase 的边界；其余边界按 Gap 逐圈变化量切分。
- **三种 agent**：
  - Lead：解析问题；缺 Race 或缺车手时带候选项反问；拿到候选 Gap Phase 后，结合用户问题决定调查哪几段，在同一轮里并行派出 Researcher；读完结果后如有某段没解释清楚，补查一轮。
  - Researcher：每个在全新的上下文里调查一个 Gap Phase，用专用分析工具查圈速、轮胎与胎龄、进站、赛事事件、位置与超车，返回带 Evidence 编号和 Support Level 的 Explanation。
  - Writer：只看用户问题和 Researcher 的结果，写出带 Evidence 编号的报告。
- **上限由代码强制**：一次 Research 最多 4 个 Researcher、补查 1 轮，每个 agent 有轮数上限。
- **专用分析工具**：输入是 Race、车手、圈数范围；数字全部由程序计算；每次调用登记一条 Evidence（编号、数据表、Race、车手、圈数范围、数据行）。不提供自由 SQL。
- **引用校验**：报告生成后，程序检查其中每个 Evidence 编号都在本次对话登记过；不通过时让 Writer 重写一次，仍不通过则去掉无效编号并标注。
- **接口**：`POST /chat` 保持 Project1 的结构（`response`、`session_id`、`tool_calls`），每条 `tool_calls` 带 `agent` 字段；响应里额外带画图用的 Gap 数据和 Evidence 明细。另有一个实时进度流供前端显示研究过程。
- **会话**：保存在进程内存里，记住 Race、Driver Pair 和已有 Evidence；追问触发一次更聚焦的 Research。Cloud Run 最大实例数为 1。
- **模型**：Lead 和 Writer 用 `gemini-3.5-flash`，Researcher 用 `gemini-3.5-flash-lite`，经 LiteLLM 走 Vertex AI，编排用 OpenAI Agents SDK。
- **前端**：单页。左侧聊天流，顶部是简介和示例问题；报告在对话里渲染，Gap 曲线由前端根据响应里的数据绘制；Evidence 编号可点开。右侧是研究过程栏。界面英文，报告语言跟随提问语言。
- **部署**：GCP 项目 `agentic-project-1-510502`，服务 `f1-gap-research`，区域 `europe-west1`，仅 `columbia.edu` 可访问，步骤按 `DEPLOYMENT.md`。

## Testing Decisions

- 好的测试只检查外部行为：给定一小段手工构造的逐圈数据，断言工具返回的数字和 Evidence，而不是内部实现。
- 测试接缝一：分析层的对外函数（Gap、候选 Gap Phase、各专用分析工具、Evidence 登记、引用校验）。这部分先写测试再实现，用小型手工数据集，不依赖真实快照和网络。
- 测试接缝二：`POST /chat` 的响应结构，把 Research 替换成固定结果后断言字段和 `agent` 标记。
- agent 的提示词和前端不写单元测试，用真实运行验证：三个示例问题、一个模糊问题、一个数据答不了的问题。
- 参照：Project1 的 `tests/` 用 pytest，沿用同样的方式。

## Out of Scope

- 排位赛、冲刺赛、练习赛，以及 2026 以外的赛季。
- 遥测数据（油门、刹车、车速曲线）和车队无线电。
- 两名以上车手的比较，以及赛季层面的统计。
- 预测未来比赛。
- 用生图模型画图。
